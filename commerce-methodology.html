How Commerce Observation Works

The Demos agent commerce protocol uses a set of public attestation authorities — independent third-party services like GLEIF, FINRA, and the ECB — for credential verification and reference data. The Oracle monitors whether these authority endpoints are reachable.

What the Oracle observes

The Oracle runs a dedicated probe service that periodically contacts public API endpoints operated by independent attestation authorities. For each authority, it records whether the endpoint responded, how quickly it responded, and whether the response matched the expected format.

These authorities include organizations like the Global Legal Entity Identifier Foundation (GLEIF), the Financial Industry Regulatory Authority (FINRA), the European Central Bank (ECB), and the Federal Risk and Authorization Management Program (FedRAMP), among others. Most probed endpoints are public APIs operated by the authority itself. A few are public services that carry an authority's data: the ECB's reference rates are read through Frankfurter, a service that republishes them, and the DNS check goes through Cloudflare's public DNS resolver. Where that is so, the state says whether that service answered, not the authority. Most probes need no key; a probe that needs an API key or an RPC address runs only where the probe runner has one (see unsupported below).

The probe runs about every 5 minutes (±30 s) as a separate service from the Oracle's network monitoring. A cycle allows 60 seconds in total; a probe not reached in that time is left out of that cycle's results. Commerce observation results never influence the Oracle's core network assessments (status, trend, risk, agreement, confidence, or data quality as reported on the homepage and through /organism).

Reachability states

Each authority endpoint is classified into one of these states after every probe cycle. A probe allows 5 seconds.

StateMeaning
healthyThe endpoint answered within the timeout with a status code the probe expects (for some authorities a 404 or a named 4xx is the expected answer to a probe without input) and, where the probe checks the body, a JSON body of the expected form. A body that is not JSON is not checked.
degradedThe endpoint answered, but rate-limited (HTTP 429), with an unexpected status code, or with a body that failed the probe's check.
unavailableThe endpoint did not answer within the timeout, failed DNS, TLS or another network step, answered HTTP 401 or 403 (authentication refused), or returned a server error (5xx).
unknownThe probe stopped on an error in the probe itself; nothing was observed. It still counts as an active probe that did not answer.
unsupportedThe probe needs an API key or an RPC address the probe runner does not have, or the authority has no endpoint the Oracle can reach (for example a vendor-side session). Such an authority is not probed, not counted, and not listed in /commerce/observations.

The probe runner also records each response time as a latency class — fast under 0.5 s, normal under 2 s, slow under 5 s. The latency class does not change the state, and /commerce/observations does not publish it.

Freshness

Some authorities publish data on known cadences. For those, the Oracle reports whether the endpoint has answered healthy within that update window.

StateMeaning
freshThe endpoint's last healthy answer is within the authority's update window.
staleThe endpoint has not answered healthy within the authority's update window.
unknownThe authority was not probed, or has not answered healthy since the probe runner last started.
not_applicableAuthority has no defined update cadence.

Freshness is about the Oracle's own answers from the endpoint, not the age of the authority's data: an endpoint can answer healthy with data of any age. The time of the last healthy answer is kept in memory, so it starts again when the probe runner restarts.

Overall assessment

The Oracle derives an overall commerce observability state from the active probes (authorities marked unsupported are not counted). "Answered" means healthy or degraded.

StateCondition
healthy90% or more of the active probes are healthy.
degradedOtherwise, 70% or more answered.
partialOtherwise, 40% or more answered.
unavailableUnder 40% answered.
unknownNo active probe is configured, or the probe runner's file could not be read.

Data quality and confidence (Layer 2)

The commerce page shows two values that share names with the reading's fields and mean something else. They are computed from the probes alone and never enter the reading.

ValueRule
data_qualitysufficient when 70% or more of the active probes answered; partial from 40%; insufficient below, or when the probe runner's file could not be read.
confidenceuncertain when, in one cycle, some probes are healthy and some unavailable, or when the probe runner's file could not be read; otherwise clear.

Layer separation

Commerce observation is Layer 2. It is completely separate from the Oracle's core network assessment (Layer 1). The Oracle's homepage status, trend, risk, agreement, confidence, and data quality assessments are derived from the public seeds, and from validators that stand in when fewer than two seeds give their own height. Commerce probe data has no influence on these assessments.

This separation is architectural, not cosmetic. The commerce probe runner is a separate process from the network monitoring agent. Different code, different cycle, different output file, different failure domain.

What the Oracle does not do

The Oracle does not certify any counterparty, transaction, or commerce flow, and does not judge whether one is lawful or meets a regulation. It does not perform sanctions screening. It does not verify individual commerce claims. It does not recommend transactions.

The Oracle observes whether the public infrastructure that the Demos commerce protocol depends on is reachable. That is the beginning and the end of its commerce observation mandate.

Testnet context

The Demos agent commerce protocol is currently in development on testnet. Most authority endpoints probed by the Oracle are production public APIs operated by independent third parties — they are not testnet infrastructure. The exception is the on-chain check, which reads a contract on Base Sepolia, a public testnet, where the probe runner has an RPC address for it. The Oracle bridges both contexts: it probes real-world infrastructure while being transparent that the commerce protocol using that infrastructure is not yet on mainnet.

The Demos Network Oracle observes whether attestation authority endpoints are reachable. This is infrastructure observability, not certification.
