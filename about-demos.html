What Demos is

The Demos docs describe the Demos Network as an interconnectivity layer across chains and web contexts. The network has two parts, the node and the SDKs, and its nodes “can act either as validators or as synced read-only nodes” (architecture). Consensus is PoR-BFT, “Proof of Reputation (PoR) Byzantine Fault Tolerance” (consensus).

Parts the docs name

Consensus
PoR-BFT. Validators are shuffled into shards for each block; see below.
State
The Global Change Registry (GCR) holds account and subnet properties once blocks are synced (GCR).
Identity
Cross Context Identities (CCI): each address carries an identities object in the GCR (CCI).
Cross-chain
The XM SDKs “help you create payloads to interact with other blockchains from DEMOS” (XM).
Web2
DAHR relays an HTTP request and anchors hashes of the response on chain; TLSNotary produces proofs from TLS sessions (Web2). See DAHR.
Privacy
L2PS, the Layer 2 Privacy Subnet, “a privacy-preserving transaction layer that enables encrypted transactions” (L2PS).
Where DNO stands

DNO is an independent observer built by XM33, not part of Demos. Its public reading comes from three public Demos endpoints read from outside. It does not operate the protocol, admit validators, or decide anything on the network.

Two mechanisms, two questions

DNO's cross-check compares public answers. Demos shard composition is a consensus step inside the network. They answer different questions, and DNO never sees the second one.

DNO's cross-check

DNO, from outside

Question
Did the public seeds answer, and do the heights they report agree?
Inputs
The /info answers of three public Kynesys seeds. A seed's height is its own peerlist entry; a seed that does not list itself has no height here.
Output
status on /organism, always with status_reason.
Also dialed, not in status
The cross-check RPCs (DAHR is attempted there), fixnet peers for the reference table.

Demos shard composition

The network, for every block

Question
Which validators form the shard for this block?
Inputs
Validators that are ACTIVE on chain, and the CVSA seed.
Output
The shard that runs consensus for that block.
What DNO sees of it
Nothing.

So a stable reading means the public seeds answered and their reported heights agree. It does not mean a shard formed, that a given identity sat in one, or that the network is healthy in the sense the Demos docs use.

Validators

In the Demos docs, a validator is “an on-chain row in the validators table”. Its status moves through three states, driven by three transactions: validatorStake, validatorUnstake and validatorExit (validator lifecycle).

“Stake doesn't currently weight the random pick (Phase 2), but it gates eligibility (you must be ACTIVE).”

Demos docs · Validator lifecycle
What DNO sees of this

Nothing. DNO does not read the validators table, so it cannot say whether any identity is ACTIVE, UNSTAKING or EXITED, or what it has staked. The identities in DNO's catalog are names listed on public peerlists, not validator rows.

A shard for each block

“PoR-BFT shuffles the eligible validator set into per-block shards using the CVSA seed — a deterministic SHA-256 over recent block hashes”

Demos docs · Decentralization in PoR-BFT

Because the seed comes from recent block hashes, the same page says “no operator can predict or influence which validators land in their shard”.

Phase 1: out-of-sync validators are skipped

“validators that fail health/sync checks are skipped during shard composition for the affected blocks”

Demos docs · Enhanced security

The docs name the causes as “bad latency, divergent state, or active malice”, and say plainly that this is not a penalty: “Phase 1 does not slash, burn, or otherwise penalise stake.” Slashing, “active stake removal as a punitive response to provable misbehaviour”, “is a Phase 2 feature.”

Inside a shard

“Per-shard consensus itself runs sequentially — one consensus round per shard at a time — not multiple rounds in parallel within the same shard.”

Demos docs · Unparalleled scalability

The parallel part is applying transactions. Within one block, independent transactions are split into groups and up to 8 groups are applied at once; the gain “lives in transaction-application within a block”, “not in concurrent consensus rounds”.

What DNO sees of this

A height that moves, or does not. A designed pause and a fault look the same from outside, so DNO never says why a height stopped.

A node's own health

Every Demos node answers an unauthenticated GET /health on its RPC port. The status is the node's own word (health and readiness):

StatusWhat the docs sayHTTP
ok“All subsystems healthy, main loop alive.”200
degraded“At least one non-critical subsystem is failed, but the chain and main loop are alive.”200
dormant“The node booted with an empty peer list and intentionally skipped signaling/MCP/TLSNotary/main loop.” Sent with an X-Demos-Dormant: true header.200
failing“The mempool/DB is unreachable, the chain subsystem failed, or the main loop died (and the node is not dormant).”503

On readiness, the same page adds that “a probe wanting to gate traffic until consensus participation can additionally inspect dormant / the X-Demos-Dormant header or require boot.complete === true”.

What DNO sees of this

None of these words. DNO reads each seed's /info, not its /health, and none of these statuses appears in DNO's reading. The peerlists DNO reads carry an online flag and one more status flag for each listed peer. DNO shows the online flag as peer-reported and leaves the other flag out, because the pages linked here do not say what it means.

DAHR

DAHR is the Data Agnostic HTTPS Relay (DAHR API reference). A client using the SDK calls createDahr(), then startProxy({ url, method }). A Demos node forwards the request to the target, returns the response, and hashes it.

  1. 1client → Demos nodestartProxy({ url, method })
  2. 2Demos node → target URLforwards the requesthttp or https only
  3. 3target URL → Demos nodethe response
  4. 4Demos nodeSHA-256 of the body, SHA-256 of the headersheaders are canonicalized first: keys lower-cased, volatile and hop-by-hop headers dropped, sorted by key
  5. 5on chainone web2Request transaction per callit stores the hashes, not the data; the pages linked here do not say which party signs and broadcasts it
  6. 6SDK → clientthe response, its hashes and the txHashreturned once the transaction is confirmed and broadcast; txHash is optional in the result type

“Each startProxy call creates one on-chain web2Request transaction that stores only hashes of the response (body and headers), not the full data.”

Demos docs · DAHR API reference · Web2 proxy · types

What one call records

  • SHA-256 hashes of the response's body and headers, in one on-chain web2Request transaction.
  • Anyone holding the same response bytes can hash them and compare.

What it does not

  • Store the response itself: only hashes go on chain.
  • Say whether the content is correct, current or complete.
  • Prove the TLS session. That is TLSNotary, a separate mechanism the docs list as slower (about 2–5 s against about 500 ms) and costlier (1+ DEM plus gas, against gas only).

Same letters, different object: the Key Server OAuth flow returns a DAHRAttestation, an Ed25519-signed record that the Key Server performed a verification (Key Server OAuth). DNO does not use it.

What DNO does with DAHR

  1. Each cycle DNO dials its cross-check RPCs. For each one that answers, it asks a Demos node, through the SDK, to relay a GET of that RPC through DAHR.
  2. It counts an attestation only when a transaction hash comes back, and keeps the URL, the transaction hash, the response hash, the HTTP status and the time.
  3. When on-chain publication is enabled, DNO attaches those records to its fleet alerts and daily summaries, never to the public reading. On-chain publication is disabled, so DNO posts none of them. The relays themselves still happen: per the Demos docs each relay call creates a web2Request transaction, and DNO counts a relay when a transaction hash comes back, without checking that the transaction was included.
  4. /health reports the state in attestation: available, last_count (how many of those relays returned a transaction hash this cycle) and last_ok_at.
Not the seeds

The three seeds whose answers enter status are not relayed through DAHR, and /organism carries no attestation. That is why the homepage says Observe. Explain. and mentions DAHR once, under the API: the sentence about the cross-check RPCs while attestation.available is true, and “DAHR attestation unavailable” while it is false.

What DNO cannot see

  • Who is in a shard.
  • The validators table: which identities are ACTIVE, UNSTAKING or EXITED, and any stake.
  • Votes, admission, and the health and sync checks consensus applies.
  • A node's own /health status.
  • Whether a peer-listed identity is a validator, or whether it answers: DNO does not dial the catalog.
  • Why height stopped. A designed pause and a fault look the same from here.
